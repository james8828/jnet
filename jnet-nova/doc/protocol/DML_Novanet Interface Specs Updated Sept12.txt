1 Introduction 
1.1 Purpose 
This document is the Software Requirements Specification for the Nova NovaNet implementation of 
the POCT1-A Device Messaging Layer (DML) protocol.  It describes the details of the messages 
transmitted between the Instrument Controller/Observation Concentrator (NovaNet) and DML 
devices (lab computers, analyzers, meters, etc). 
1.2 Scope 
This document details the fields used in each of the messages.

1.5 Message Flow for DML Instruments/Meters 
A DML device connecting to NovaNet must follow the Basic Messaging Profile as described in the 
POCT1-A document where NovaNet acts as the Observation Reviewer.  It may or may not then 
proceed to the Continuous Mode: 
 
• When a device connects to NovaNet, it must initiate a dialog by sending a Hello message as 
described below. 
• When the Hello message is acknowledged, the device must then send the Device Status 
Message described below to continue the dialog. 
• The device must respond then and at any time thereafter to a Request Observations message 
by sending an Observations message - or an End of Topic message if there are no 
Observations. 
• The device must then respond to the Observations message Acknowledgement by sending 
another Observations message - or an End of Topic message if all Observation messages 
have been sent. 
• The device must respond then and at any time thereafter to a Request Device Events message 
by sending a Device Events message - or an End of Topic message if there are no events. 
• The device must then respond to the Device Events message Acknowledgement by sending 
another Device Events message - or an End of Topic message if all Device Events messages 
have been sent. 
• The device must respond then and at any time thereafter to a Location, Operator, Patient, 
Physician, Reagent or Setup list message by sending an Acknowledgement message.  It must 
process the message and expect more list messages until an End of Topic message is 
received. 
• The device must respond then and at any time thereafter to a Start Continuous Directive 
message by sending an Acknowledgement message if capable of Continuous Mode 
communication or an Escape Message if not. 
• If a Continuous Mode Directive has been acknowledged, the device must enter Continuous 
Mode until a Terminate message is received from NovaNet. 
• In Continuous Mode the device may send Observation, Device Event, Keep Alive, or Vendor 
custom messages to NovaNet at any time (except when NovaNet is expecting an 
acknowledgement). 
• In Continuous Mode the device must receive and acknowledge Directive, Location List, 
Operator List, Patient List, Physician List, Reagent List, Setup List and End of Topic 
messages. 
• If a Terminate message is received in Continuous Mode the device must acknowledge and 
terminate the current conversation. The device may then reconnect to NovaNet.  Currently 
NovaNet does not terminate Continuous Mode.

2 Third Party Interfaces 
The DML protocol shall be adapted for use in two non-device interfaces between NovaNet and 
THIRD PARTY services, a Result interface for reporting results from NovaNet to THIRD PARTY 
and an Operator interface for sending operator lists from THIRD PARTY to NovaNet. 
2.1 Result Interface 
• NovaNet shall initiate a session with the receiving system (THIRD PARTY) for each result to be 
sent as if it were the device sending the results. 
The Device object of the Hello record shall contain the identifiers of the device on which the 
analyses were performed. 
 
• This interface will not be capable of receiving operator lists or patient lists. 
The Device Static Capabilities object of the Hello message shall not list these capabilities for 
the Result interface.  These lists must be transmitted on separate interfaces. 
 
• This interface will send reagent information with results (name, lot_number and 
expiration_date). 
 
• This interface will send the operator ID of the operator responsible for each observation (if 
available). It will not send the operator's name. 
 
• This interface can send comments associated with the sample and/or an observation, including 
the chartable and flagable flags, using the following format: 
<comment.text V="text of the comment">CH={0,1}^FL={0,1}</comment.text> 
for example: <comment.text V="insulin given">CH=1^FL=0</comment.text> indicates that 
this comment is chartable but not flagable. 
• This interface will communicate the location and facility where the instrument (that produced the 
result) was located at the time when the result was transmitted, using the following format: 
<DEV.device_name V="device name">facility^location</DEV.device_name> 
for example: <DEV.device_name V="ICU-4 Glucose">Cambridge 
Hosp^ICU</DEV.device_name> 
The receiving system should add this location (where the instrument was at the time the test 
was run) as a note in their system. 
 
• This interface shall send the patient's location at the time the sample was drawn (location field in 
patient object) in the following format: 
<PT.location V="facility^location^room^bed (or facility^location if room and bed are not 
available)"/> 
for example: <PT.location V="Cambridge Hosp^ICU^101^1/> 
• NovaNet shall terminate the session (but not the connection) at the end of the DML Basic Profile 
Flow. 
The Device Static Capabilities object of the Hello message shall define the connection profile 
as Synchronous Acknowledgement (SA).

NovaNet shall then initiate a new session for each new result set as they are received from 
analyzers.  Note that, with meters, the usual pattern will have a series of sessions as multiple 
results are downloaded from the meter followed by an indefinite period until the next meter 
is attached for the next batch download. 
2.2 Operator List Interface 
• This interface will initiate a single session and will stay connected after being asked to go into 
continuous mode. 
The Device Static Capabilities object of the Hello message shall list continuous mode as a 
capability and the connection profile as Synchronous Acknowledgement (SA) 
 
• This interface will be capable of receiving both incremental and complete operator lists for all 
locations supported by the NovaNet system. 
The Device Static Capabilities object of the Hello message shall list both these capabilities 
for the Operator List interface. 
 
• This interface is not intended for receiving patient lists or sending results. 
 
• The sending system (THIRD PARTY) will send complete operator lists when NovaNet is first 
brought on-line. Otherwise it will generally send incremental lists. 
The Device Status message shall give the last update time for operators.  From this and its

• The cardinality of the Nova Setup Message is one-or-more. Therefore, an Observation

6.20.2.1 The Relationship between the KeyValues Object and the Test 
Configur
ation Objects 
• The KeyValues Object and the Test Configurations Object contain may contain settings that 
are related to each other. One setting in one object may not work correctly if the 
corresponding setting in the other object does not have a correct value. 
• Therefore, to maintain the integrity of the KeyValues settings and the Test Configuration 
settings, the device shall use the following rules: 
o Any setting in the KeyValues Object that is found to contain invalid value or has 
invalid format shall cause all of the settings in the KeyValues Object and all of the 
settings in the Test Configurations Object to be discarded. 
o Any setting in the Test Configuration Object that is found to contain invalid value or 
has invalid format shall cause all of the settings in the Test Configurations Object and 
all of the settings in the KeyValues Object to be discarded. 
o The rules on how an entry in the KeyValues Object or an entry in the Test 
Configurations Object contain invalid values or has invalid format shall be detailed 
later in their own sections. 
o All of the KeyValues settings and all of the Test Configuration settings must be 
downloaded to the device during the Setup topic.

6.20.7.1 Attributes of the <QC>, <LINEARITY>, and <PROFICIENCY> 
elem

• The following section lists the attributes of the <QC>, <LINEARITY>, and 
<PROFICIENCY> element: 
 
<interval_type V=”value” /> 
<alert_mins V=”value” /> 
<time V=”value” /> 
<result_valid_time V=”value” /> 
 
• The <interval_type> element contains the type of time interval to configure for QC. The 
value of the <interval_type> element shall dictate the content of the <time> element. 
The valid values of the interval_type element are: 
o SHIFT : 
The QC configuration is configured by shift times. 
The <time> element shall then contain a string of shift times separated by the “*” 
character. Each shift time shall have the format “HHMM”, where HH is the hour in 
24-hour format, and MM is the minutes. 
 
Example: <interval_type V=”SHIFT” /> 
<time V=”0130*0930*1730” /> 
 
< interval_type V=”SHIFT” /> 
   <time V=”0100*0500*0900*1300*1700*2100” /> 
 
o ELAPSED: 
The QC configuration is configured by elapsed hours. . The <time> element shall 
then contain the number of elapsed hours. 
 
Example: <interval_type V=”ELAPSED” /> 
<time V=”8” /> 
 
o EXACT: 
The QC configuration is configured at a specific date and time. The <time> element 
shall then contain a string that specifies the date and time. The format of this string 
shall adhere to the TS data type of the POCT1 standard. 
 
Example: <interval_type V=”EXACT” /> 
<time V=”2007-07-01T13:30:00-05:00” /> 
 
• The <time> element contains the time interval of the QC tests. Its value is dependent on the 
value of the <interval_type> element. See examples in the <interval_type> element. 
• The alert_mins element contains the number of minutes prior to a scheduled QC test to 
alert the user.

6.20.7.2 The <qc_cfg_test> element 
• The <qc_cfg_test> element contains the QC configuration for a specific test. The following 
section lists the attributes of the <qc_cfg_test> element: 
 
<name V=”value” /> 
<mode_cd V=”value” /> 
<level_req level=”value” repet_req=”value” /> 
<allow_stat_qty V=”value” /> 
 
• The <name> element contains the test name. 
Example: <name V=”Glu” />, <name V=”Creat” /> 
 
• The <mode_cd> element contains the QC mode. Valid values are: 
o NONE:  No QC is configured for the specific test. 
o NOTIFY: User is notified when QC is due. 
o LOCK: Device is locked when QC is due. 
 
• The <level_req> element contains a level that QC must be passed and the number of times to 
repeat for that level. The level attribute contains the level(s). The repet_req attribute 
contains the number of times to repeat for that level. 
 
A series of <level_req> elements shall be used when more than one level is required to pass 
QC for a specific test. The following example specifies that level 1, 2, and 3 are required and 
5 tests must be done for each level. 
 
  <level_req level=”1” repet_req=”5” /> 
  <level_req level=”2” repet_req=”5” /> 
  <level_req level=”3” repet_req=”5” /> 
 
• The allow_stat_qty element contains the number of measurements that can be taken for a 
specific test after QC is due and <mode_cd> is LOCK. This attribute is only meaningful 
when the value of the <mode_cd> element is LOCK. 
6.20.7.3 Empty <QC_CONFIG> element 
An empty <QC_CONFIG> element in the following format shall be used to specify that the device 
has no QC configuration: 
 
<QC_CONFIG></QC_CONFIG> 
 
If the device is currently configured for QC, all of the QC configuration settings shall be removed 
from the device.
